- More lookups rest as one row that says what they found, and a click opens the whole answer.
- A `code` card folds a printed dict or list to a tree, and shows a call's own card when the snippet only printed its answer.
- Turn decision features on and off from `/decisions`, and decision settings apply as soon as you save them.
- A decision about a tool call shows on the call's card, live while the engine works.
- Token estimates learn each model's tokenizer from what its provider billed.
- Shell cards show an ETA from a small model that learns from your own past commands, with no decision endpoint.
- Config files upgrade themselves to a new format, with a backup first and a note on every line they change.
- Caudra learns from your conversations in the background and keeps what it learned in your instruction files and project memory.
- pstack's engineering skills come built in, off until you turn them on, with their scripts ported to Rust.

> [!IMPORTANT]
> **Close every other Caudra session before you start Preview 12.** On its first start, Preview 12 upgrades the session database in your [state directory](https://caudra.ai/docs/configuration/#directory-layout) to keep what it learns about each model's tokenizer and what continual learning changed, to import your past shell commands' run times for shell ETAs, and to arm automations that ship with Caudra. The upgrade needs exclusive access. This includes other terminals, editor sessions over ACP, and `caudra storage` commands. While any of them still has the database open, Preview 12 does not start. It lists the open sessions to close instead, and nothing is changed.
>
> The upgrade keeps your sessions and saves a copy of the database from before it as `backups/caudra.db.v32.bak` in the state directory. Preview 11 and earlier cannot open the upgraded database, and `caudra rollback` restores only the previous binary.

> [!WARNING]
> **Before you start Preview 12, close older Caudra sessions so it can upgrade your config files.** `caudra.toml` moves to format version 3, and `mcp.toml` and `permissions.toml` to version 2. Preview 12 rewrites the global files when it starts, after it saves a copy of each, but only while no other Caudra process is running. Otherwise it reads them upgraded in memory and leaves them unchanged on disk, and saving to them from inside Caudra, such as with `/env` or `/mcp`, fails until Caudra starts with no other session open.
>
> Preview 11 and earlier cannot read an upgraded file. To go back, copy the file's backup from `backups/config/global/` in the state directory over it. Files in a project's `.caudra/` are never rewritten on their own. If you commit them, run `caudra config migrate --project` once everyone who shares them runs Preview 12. See [Config file versions](https://caudra.ai/docs/configuration/#config-file-versions).

### Models

- **MAI-Code-1.1-Flash on GitHub Copilot.** `copilot/mai-code-1.1-flash` and `copilot-enterprise/mai-code-1.1-flash` now have their price and size class before Copilot's model list arrives: $0.20 per million input tokens and $1.20 per million output tokens, with cache reads at $0.02 and cache writes at $0.25. GitHub lists it as a lightweight model, so Caudra counts it among the Fast models. Thinking takes `low`, `medium`, and `high`. See [Copilot](https://caudra.ai/docs/providers/#copilot).
- **GPT-6 Astra and Claude Fable 5.1 on GitHub Copilot.** `gpt-6-astra` costs $10 per million input tokens and $50 per million output tokens on Copilot, with cache reads at $1 and cache writes at $12.50. `claude-fable-5.1` costs the same, except cache reads at $0.25. Caudra used to bill it at Fable 5's $1, so a Fable 5.1 session's cost in `/usage` comes out lower from now on. Both take thinking levels from `low` to `max`.

### Changes

- **Continual learning**: Caudra now learns from how you work with it, in the background. After at least 10 messages you typed and 2 hours since the last run, once the session has been idle for a minute, a read-only learner on the new **Learn** model job reads the project's recent conversations, checks each finding against the project's history with `history.search` and `history.read`, and reports what will still hold. Caudra checks every item and writes it to a managed block in the project's `AGENTS.md` (conventions for everyone, backed by at least two sessions), `AGENTS.local.md` (your machine's setup), `~/.config/caudra/AGENTS.md` (your own preferences), or project memory notes, which the `/memory` inspector marks as the learner's. It never edits text outside its block, and leaves alone a file you changed while it worked. The status bar says when a run changed something. `/learn` lists the runs with what each changed and dropped, opens a run's transcript with `t` (live while it runs, and kept for each project's last 20 runs), runs one now with `n`, reverts a change with `u`, and pauses the project with `p`. The mouse works there as in the other modals: click a run or change to select it, click the selected run to open its transcript, and click a footer hint to press its key. It is on by default. Turn it off with `[agent] continual_learning = false`, or narrow where it writes with `learning_targets`. Its spend shows under `learning` in `/usage`. See [Continual learning](https://caudra.ai/docs/learning/).
- **More lookups fold like a file read**: `history.search`, `history.read`, `history.sessions`, `tool_output`, `skill`, `host.environment`, `list_sessions`, `read_topic`, and `automation` calls now rest as one row in every `/view`, and so do the calls of `plan`, `workflow`, and `task_control` that only read: reading the plan, listing, validating, and checking the status, details, or history of a workflow run, and listing tasks or checking one. A click on the row opens the whole answer and the next folds it, on its own card and as a row of a `code` or `batch` card. The row says what the call found, such as how many hits a search kept, which session a read came from, how many runs or automations a listing holds, a run's or task's state, whether a script is valid, or that the plan is empty. Plan writes, workflow starts and controls, and cancelling or backgrounding a task keep their cards open, and `websearch` is unchanged. The new `plan_read`, `workflow_read`, and `task_control_read` entries of the default `ui.always_collapsed` list cover those reading calls. If you set your own `always_collapsed` list, add the entries you want from the [default](https://caudra.ai/docs/configuration/#ui) to get this.
- **Printed dicts and lists fold to a tree**: When a `code` snippet prints a dict or a list on a line of its own, as `print(r)` or `json.dumps(r)` writes it, or returns one, the card now shows it as a folded tree, one row such as `▸ {…} 7 keys`, in place of a wall of text. A click on that row opens the whole tree, a click on any `{` or `[` row inside folds or opens that part, and a click on the first row folds the tree again. An opened tree is drawn whole rather than in the card's scroll window. The raw view of an MCP call's card now draws its JSON as the same tree, open, so you can fold the parts you don't need. When the tree only repeats what one of the snippet's calls answered, such as `print(await host.environment())`, that call's card also shows open, and a click folds it. Anything else the snippet prints, such as `print(len(hits))`, is drawn as before, and the model still reads all of it as text. See [In the transcript](https://caudra.ai/docs/code/#in-the-transcript).
- **Tool titles set apart what a call names**: A skill's card now reads `Skill loaded <name>`, and `Loading skill` while it runs. Every card title now sets the names and paths it shows in italics, as it already did for the text a search looked for: file paths, URLs, skill and note names, a workflow's or automation's name, and run, task, firing, and output IDs.
- **Job, workflow, and automation cards read like the others**: A `task_control`, `workflow`, or `automation` call was titled with the tool's name and its raw action, such as `⚙ task_control status shell-66`. Each now has its own title, with the action as a verb that says how far the call got: `◷ Jobs checking shell-66` while it runs and `◷ Jobs checked shell-66` once it is done, `⑂ Workflow started review`, or `↻ Automation read history greeter`. A call that failed keeps the plain verb, such as `Jobs check shell-66`.
- **Cards say what a result costs the context**: A card whose result the model reads now gives an estimate of its tokens beside what it found, such as `209 lines · ~2.1k tokens` on a file read or a skill, `exit 0 · ~840 tokens` on a command, or `12 matches in 3 files · ~610 tokens` on a search. File reads, globs, greps, file indexes, commands, `code` runs, skills, subagent answers, and source-code lookups now say it, as web pages, MCP results, and `tool_output` reads already did. An instruction file a read pulls in, such as an `AGENTS.md`, says its own count on its row. See [Watching it work](https://caudra.ai/docs/token-economy/#watching-it-work).
- **Token estimates learn each model's tokenizer**: Caudra counts tokens locally with OpenAI's tokenizer, which can be well off for other models. It now compares that count with what the provider billed for the results a tool loop added between two requests, and learns from it how many tokens one local token is on each model. Card counts, the `/context` breakdown, the tool ledger in `/usage`, and the estimate automatic compaction adds to the provider's last count all use what it learned, and what it learned is kept across sessions. A card keeps the count it had when its result arrived, and a reopened session counts its cards with what the model's tokenizer is known to be now. Tool ledger rows recorded before this update keep their uncalibrated counts. See [Watching it work](https://caudra.ai/docs/token-economy/#watching-it-work).
- **`code` cards keep a clock**: A `code` card's header now counts up while the snippet runs and then shows how long the run took, such as `· 2.4s`, as a `shell` card does. A `code` row inside a `batch` does the same. Runs saved before this update show no time. See [In the transcript](https://caudra.ai/docs/code/#in-the-transcript).
- **Time and usage move into the `⋮` menu**: Tool card headers no longer end in the time and the request's usage, such as `135.9k↑ 872↓ $0.055  09:26:15`. The first line of a message's `⋮` menu shows them now, with the date when the message is not from today. Every prompt, reply, reasoning block, and tool call has a time there, including those of a restored session, which come from each message's saved ID. A message of the turn that is still running opens the menu too, with its actions once the turn is saved. A subagent's transcript now has `⋮` as well, showing the details without fork or revert. See [Message actions](https://caudra.ai/docs/sessions/#message-actions).
- **Turn decision features on and off from `/decisions`**: On the Features tab, click one of the selected feature's modes to switch to it, or press `Space` or `Enter` to move to its next allowed mode, such as `off`, `shadow`, then `enforce`. The mode under the pointer is highlighted. Caudra saves it under `[decisions.features]` in the global `caudra.toml`, keeping your comments, and every open session uses it at once. A project `caudra.toml` that turns the feature off still wins, and the footer says so. See [the decision engine](https://caudra.ai/docs/permissions/#decision-engine-advice).
- **Decision settings apply as soon as you save them**: While the terminal UI runs, an edit to `[decisions]` or `ui.show_decisions` in `caudra.toml`, to the active decision endpoint's table in `providers.toml`, or to `decisions/permission.json` now applies at once in every open session, without `/reload`. Removing the active endpoint's table turns decisions off, and a file that fails to load keeps the engine in use. See [Hot reload](https://caudra.ai/docs/configuration/#hot-reload).
- **Decisions about a call ride on its card**: A decision about a tool call, such as a `source_code_context` rerank or Auto screening, no longer draws its own row under the card. The card's header shows a chip while the engine works, such as `◆ reranking…`, and then what it did, such as `◆ reranked`. Opening the card shows the decision's line and the scores behind it at the top of its body. Chips that warn, such as `◆ asked you`, `◆ may write`, `◆ flagged`, or a failed call's chip, are drawn in the warning colour so a folded card still shows them. Three or more decisions on one card read `◆ 3 decisions`. A call inside a `batch` shows its chip on its own row. Decisions about a turn, such as a memory recall or a skill suggestion, keep their rows. `ui.show_decisions = false` hides the chips and their lines as soon as you save it. See [Decision rows in the transcript](https://caudra.ai/docs/permissions/#decision-rows-in-the-transcript).
- **Rerankers judge a wider pool in one request**: With a [decision endpoint](https://caudra.ai/docs/providers/#decision-endpoints), a rerank now sends up to 64 candidates in one request instead of 16 at a time, so the engine reads the shared question and query once. `memory_search` judges up to 64 keyword matches instead of 32, and `history_search` sends its 64 in one request. `source_code_context` judges the first 64 rows instead of 16 and, in `enforce`, keeps only the rows at or above `thresholds.relevance_floor`, best first. It leaves out the rest, and the rows past the first 64, unless none clears the floor. The model's note names up to eight of the rows it left out, and the card's match count follows the rows kept. A request waits one `rerank_timeout_ms` for every 16 candidates it holds, so a full one waits up to four, and `rerank_timeout_ms` now defaults to 3000 instead of 2000, since a local engine took 6 to 8 seconds over 64 candidates. `decisions.rerank()` in `code` and `rerank()` in a workflow send 64 candidates to a request too. A workflow run paused in the middle of a `rerank()` on an older release fails when it resumes. Memory recall, compaction retention, and output pointers still judge up to 16. See [Reranking](https://caudra.ai/docs/configuration/#reranking).
- **Shell ETAs from your own runs**: A shell card's ETA now comes from a small model that runs on your machine and learns from the commands you run, in place of the `shell_duration` decision feature. It needs no decision endpoint and sends nothing anywhere. A command like one you ran before shows how long that took, such as `ETA ~40s`. Otherwise the card says `ETA seconds` or `ETA minutes` when the model is confident, and nothing for a command that exits at once or one it is unsure of. It only labels the card: timeouts and background delivery follow `agent.shell_execution` and `agent.shell_async_threshold_secs` alone. On its first start, Preview 12 fills it from the newest 20,000 shell calls your saved sessions hold, keeping only hashes of each command's words, never the command. The first shell command after Caudra starts waits while the model trains, and every finished command teaches it once more. It is on by default. Turn it off with `[agent] shell_eta = false`. The `shell_duration` feature, its `shell_duration` and `shell_endless` thresholds, its duration history, and its decision log rows are gone, and the config upgrade comments out those keys. See [`agent`](https://caudra.ai/docs/configuration/#agent).
- **pstack built in**: Lauren Tan's [pstack](https://github.com/cursor/plugins/tree/main/pstack) skills for Cursor now ship with Caudra under their MIT license, together with the `deslop`, `control-cli`, and `control-ui` skills from Cursor's team kit. Turn them on with `[plugins.skill] pstack = true`. The agent then sees one `pstack` skill, whose index lists every skill and whose pages load by address, such as `pstack/poteto-mode` or `pstack/poteto-mode/playbooks/bug-fix.md`. The pages come translated, naming Caudra's tools, paths, models, and commands, so the agent follows them as written. Each skill you run directly gets a `/pstack:<name>` command, the `pstack-poteto-agent` and `pstack-comment-sicko` task profiles appear, and pstack's scripts become `pstack` calls in `code`: `log`, `check_plan`, `worktree_audit`, `watch_pr`, and `orch`, ported to Rust so they need no Bun, Node, or Bash. In Plan mode, poteto-mode writes its plan with the `plan` tool and checks it with `pstack.check_plan("--plan")`, and `orch`'s read-only commands work there too. The commands the scripts run, such as `git` and `gh`, get the same environment as shell commands, so when `gh` keeps its login in `GH_TOKEN` or a keyring, forward those variables with `/env`. A `code` run that reaches its timeout stops them. Benny's Slack triage and watch-pr's drive mode ship as [automations](https://caudra.ai/docs/automations/): with pstack and `experimental.automations` on, `pstack-watch-pr`, `benny-triage`, and `benny-reproduce` are listed in `/automations` under the new `bundled` scope, ready to arm with no file to write or trust. A project or user script of the same name replaces one. Turning pstack off removes them, and a session that had one armed disarms it when it next starts, keeping its args. `setup-pstack` writes your model roles to `~/.config/caudra/pstack/models.md`. See [pstack](https://caudra.ai/docs/skills/#pstack).
- **Config files upgrade themselves**: Every TOML config file now has a format version in its top-level `version` key, and Caudra adds the key to a file without it. When a release changes a format, Caudra upgrades your files in place and keeps your layout and comments. Above each line it changes, it writes a comment such as `# Upgraded by Caudra 0.2.0-preview.12 on 2026-10-20: renamed ...`, and your own comments on that line stay below it. A removed key is commented out rather than deleted. Global files are rewritten at startup, after a backup, while no other Caudra process is running. Project files in `.caudra/` are read upgraded and never rewritten on their own, and a notice says when one is behind. `caudra config migrate` upgrades the global files on demand, `--project` adds the project files, and `--dry-run` shows a diff without writing. See [Config file versions](https://caudra.ai/docs/configuration/#config-file-versions).
- **Old keys are upgraded instead of refused**: Keys from earlier releases that stopped Caudra with an error, or that silently stopped matching, now move to their new form when the file is upgraded:
  - `caudra.toml`: `ui.tool_output_lines.python_execution` becomes `code`, and `decisions.features.code_context` becomes `source_code_context`. In `agent.disabled_tools`, `code_context` and `code_refs` become `source_code_context` and `source_code_refs`, and `python_execution`, `mcp`, and `code` are removed, because `code` cannot be turned off. `agent.defer_builtin_tools`, `agent.max_continuation_turns`, `decisions.features.tool_search`, `decisions.allow_remote`, and `experimental.decision_engine` are commented out.
  - `mcp.toml`: the top-level `defer_tools` and each server's `always_load` are commented out.
  - `permissions.toml`: the `[code_context]` and `[code_refs]` tables become `[source_code_context]` and `[source_code_refs]`, and `[python_execution]` becomes `[code]`, so rules written under those names apply again. `[bash]` becomes `[shell]`.

  A file that sets both an old key and its new name is left unchanged, with an error that names both. The legacy decision endpoint keys in `[decisions]`, such as `base_url`, still stop Caudra with the error that shows the `providers.toml` table to write.
- **Backups have their own folder**: Copies Caudra saves before it changes a file now go to `backups/` in the state directory: the session database before a schema upgrade or a permission review repair, and each config file before an upgrade, under `backups/config/global/` and `backups/config/projects/<project-id>/`. Backups are owner-only and never deleted. Database backups from earlier releases stay beside `caudra.db`. See [Backups](https://caudra.ai/docs/configuration/#backups).

### Fixes

- **Switching decision endpoints keeps flagged content flagged**: A session whose content screening had flagged web or MCP output lost that flag when you switched the decision endpoint, which loosened its upload and credential screening. It now keeps it.
- **Every task card names its model**: A task's card showed the model its subagent runs on only when the task ran in the background. A foreground task lost it after the subagent's first turn, a task inside a `batch` lost it from its row, and no task card showed it after you reopened a session. Every task card and `batch` row now names the model while the task runs, after it finishes, and after a reload. The model appears once, after the task's progress, and no longer also in the task's `[model=…]` arguments. Those arguments also leave out `profile=builtin`. A task's answer is sized by its tokens alone, such as `~240 tokens` rather than `3 lines · ~240 tokens`. Sessions saved before this update still show the line count.
- **No false "statement of intent" nudge while work runs**: A turn that ended by saying what it would do once its delegated task reported, such as `I'll report readiness and the proposed first batch`, drew `The turn ended on a statement of intent. The work it announced was not performed.` while that task was still running, and the model spent a turn defending itself. The nudge now waits until no task, background job, or workflow is running.
- **Claude models on GitHub Copilot cache their prompts**: Claude models through `copilot` and `copilot-enterprise` never marked where the prompt may be cached, so every turn sent the whole conversation again as fresh input and `/usage` showed a 0% cache hit rate for them. They now mark the system prompt, tools, and the latest messages the way the `anthropic` provider does, so later turns read the conversation from the cache.
- **Copilot Enterprise takes a tenant name**: Answering the GitHub Enterprise hostname prompt with a name such as `company` made the login fail. A name without a dot now means `company.ghe.com`, at the prompt, with `--hostname`, and in `GH_COPILOT_ENTERPRISE_HOST`.
- **`/login` says why it failed**: When a sign-in from the TUI failed, the error read only `OAuth login process failed: exit status: 1`. It now carries the reason the login gave, such as `http: failed to resolve host name: [6] Could not resolve hostname`.
- **Caudra starts when a provider's credentials are gone**: If the model you last used belongs to a provider whose saved login was removed, such as a deleted Copilot Enterprise auth file, Caudra stopped at startup with `GH_COPILOT_ENTERPRISE_TOKEN not set and no saved credentials`. It now starts with that model and opens `/login`, even when you have set up a provider of your own.
- **One token reads `~1 token`**: Card sizes said `~1 tokens`.
- **A `code` run that waited reads cleanly**: After a snippet that slept finished, its card showed a stray separator, such as `( · 3 calls)`, and its row in a `batch` lost what it found. Both now read like any other run.
- **A stray indent no longer stops a `code` run**: A snippet with a line indented deeper than the one before it, such as ` datetime.datetime.now()` after `import datetime`, did not run: `Unexpected indentation`. Python allows a deeper line only after one ending in `:`, so Caudra now lines such a line up with its block, together with the lines under it, and the card lists the fix. Strings, comments, and lines continued inside brackets keep their indentation. See [Results and errors](https://caudra.ai/docs/mcp/#results-and-errors).
